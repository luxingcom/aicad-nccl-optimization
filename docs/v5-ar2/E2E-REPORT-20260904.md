## 3. fence-arm 设计（最终方案）

问题本质：ar2 严格要求同一逻辑 op 在 4 rank 走同一后端；任何 per-rank 本地判据（捕获态、对齐、计数）在启动期无全局栅栏时都可分歧。

方案（`collectives.cc` 锁存 + `ar2_core.cpp::ctrl_arm_fence`）：

1. **锁存**：进程见过首个 CUDA graph 捕获事件前一律不分发（dummy run 等启动大 AR 天然安全走原生）。
2. **触发点**：捕获后首个 `bytes > crossover` 的 eager AR——TP 集合必在全 rank 同逻辑到达，且自身恒走原生。
3. **栅栏**：触发点上经 ar2 控制面（rank0:9520 持久星型连接）做 'F'/'G' 集合，四端到齐才 `armed`；之后稳态服务是 SPMD 锁步，逐 op 分发决策天然一致。栅栏失败（10s 超时）→ 永久放弃武装，全原生（错误方向=安全方向）。
4. **兜底**：任何 ar2 op 失败 → 永久禁用 + 本 op 原生重做（M1 用户缓冲区在两轮完成前不被写回，可证明安全）。
5. `AR2_V5_EAGER=1` 逃生门：无图测试负载（bench_coll）立即分发。

实测：四端 `armed via fence`，dspark FULL 捕获 11/11 全速（36.5it/s，对比 E2E #1 的 34→1.3it/s 停顿），health=200。

## 6. 结构性定谳：为什么 E2E 持平（重要）

- **稳态 decode 通信不可达**：全程 ~2.5h 满载基准零条 `progress: dispatched`（<65536 op）。若 decode 小 AR 经 hook，按 W9-R9 审计口径（86+42 AR/step × ~5 step/s）应产生 ~5.8M op / ~89 条报点。 ⇒ decode 的 TP 通信全部在 CUDA graph **重放**内执行，不经过 `ncclAllReduce` C 入口。
- **稳态 prefill 通信无目标**：prefill 步 AR 尺寸 = tokens×hidden×2（4096×7168×2=56MB 级），全部 >crossover，本就路由原生。
- 结论：**NCCL-hook 型集成在当前生产形态（FULL_AND_PIECEWISE 图 + dspark 投机）收益 ≈ 0，与 ar2 本身性能无关**。ar2 微基准在 ≤8KB 领先 9~43% 的收益要落地，必须让集合在**捕获期**被 ar2 接管（`ar2_capture_layer`/M2 图模式，vLLM 侧在 cudagraph 捕获处显式集成）——属 vLLM patch 级工程，超出 NCCL-only 交付边界，列为后续路线（见 OPEN-ISSUES #10）。
