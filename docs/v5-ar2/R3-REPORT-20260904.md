# R3 多 QP 带宽工程报告（2026-09-04）

> 执行轮: 用户指令 "同意启动容器内集成方案落地工作，分三步（R1R2R3）执行落实通讯优化" 的第三步。
> R1（按图归属细分）与 R2 门禁跳过决策见 INTEGRATION-ROADMAP.md §状态。
> **结论先行: 多 QP 条带假设被实测否定 —— nqp=1/2/4 在 14KB~512KB 全档无带宽收益（1~8µs 反向劣化）。
> 单 RC QP 已打满本链路报文流水; ar2 大消息劣势源于 2 轮阻塞协议的串行化, 非传输层并行度不足。
> 保持 AR2_QPS=1（默认, 零开销等价单 QP 形态）; R3 代码作为带数据闭环的工程资产留库, 不晋升生产。**

## 1. 设计与实现

### 1.1 动机
R1 归属显示层 AR（14KB~2.7MB）才是通信量大头, 而当前 crossover=8192 把 ar2 限制在 ≤8KB 时延区。
假设: 单 RC QP 的报文流水（doorbell/MMIO/完成通路）是 per-link 带宽瓶颈, 多 QP 条带可抬升带宽 → crossover 上调 → 大层 AR 获益。

### 1.2 实现面（全部源码已注释到位）
| 文件 | 改动 |
|---|---|
| `src/ar2_internal.hpp` | `AR2_MAX_QPS=4` / `AR2_SEQ_FLAG_WORD=16`; `Link.qp[4]+nqp`（共享 PD/CQ/MR）; `PeerInfo.qpn[4]+nqp`; `Ar2OpPtrs.flagsA/flagsB+nqp` |
| `src/ar2_core.cpp` | link_setup 逐 QP 创建; link_connect 逐 QP INIT→RTR→RTS（qpn 一一配对, QP 参数与单 QP 期一致）; **post_burst 条带**: bytes 连续切段摊到 nqp 个 QP, 每 QP 尾 8B inline 签名 WR —— q=0 写 `Ar2Ctl.dbell`（原协议不变, 兼 ABORT 通路）, q>0 写对端 seq 区 `word(16+q)`; **reap_bell 计数收齐 nqp 个 CQE**（残留 CQE 会污染下 op 的 wr_id 校验）; 建连几何校验加 nqp 一致性 |
| `src/ar2_dev_cuda.cu` | `wait_flag` device 原语（与 dbell 同字格式/同模 2^32 差容忍/abort 观测走所属链 ctl.abort）; kernel 每轮 wait_two 后补等各 QP 旗标（仅 nqp>1, 单 0 号线程自旋）; launch_one 换算 flagsA/B device VA + 启动错误留痕打印 |
| `src/ar2_dev_cpu.cpp` | `wait_flag`/`wait_link` CPU 镜像（协议机自测同构） |
| `include/ar2.h` | `ar2_config.nqp`（1..4, 0=env 回退）; `AR2_VERSION 1→2`（PeerInfo 布局变更, 拒绝混布） |
| env | `AR2_QPS`（ar2_init 对 nqp==0 回退, 默认 1） |

正确性论证核心: RC 队列内有序放置 ⇒ 后发 inline 旗标到达即本 QP 数据段已落槽 —— 与单 QP 期 "门铃到达即 bulk 落槽" 推理同源, 消费侧收齐 dbell+全旗标才动槽数据, 几何等价。
nqp=1 精确退化为 V5 单 QP 形态（不写不校验 word16+, kernel 旗标循环零次）。

### 1.3 顺带修复（审计级）
- **ar2_config_defaults env 死代码**: 原实现预填 timeout=5000/smax=65536/nslots=2 非零值, 而 env 回退只对 0 值字段生效 → `AR2_SMAX`/`AR2_TIMEOUT_MS`/`AR2_NSLOTS` 从未生效过（大尺寸微基准被静默钳在 64KB 即此因）。修正: 三字段 + nqp 填 0 哨兵, 由 ar2_init env 回退（缺省 5000/65536/2/1, 行为对未设 env 的调用方不变）。
- ar2_probe 本地 smax 改为与库同源读 `AR2_SMAX`（原硬编码致 S>smax 被静默跳过）。
- launch_one 启动失败打印 cudaGetErrorString（排障留痕, 此前错误串被吞）。

## 4. 分析与决策

1. **多 QP 无收益定谳**: 三个 nqp 档全尺寸位差 ≤3%（且单调劣化方向）——额外 WR post/CQE 收割/旗标自旋的开销可见, 带宽增益为零。单 RC QP 在本链路（CX-7 级 RoCE 直连）已饱和 per-message 流水。
2. **ar2 大消息劣势是协议串行化, 不是 QP 并行度**: 每 op 两轮 × (stage→engine_wait→post→自旋) 严格串行, host 阻塞无流水; NCCL ring 以 4 channel × 双向 × 分块持续流水（有效 ~22GB/s 聚合 vs ar2 ~2.8GB/s）。→ 任何 crossover 上调（8192→64K+）在现协议形态下不成立。
3. **决策**:
   - 生产保持 `AR2_QPS=1`（nqp=1 路径与现役生产行为零差异: 不写不校验旗标字, WR 形态相同）。
   - **R3 库不晋升生产**（libar2 `f47b21fa` 留库; 生产继续 51e36db5/343bea89 对）。defaults env 修复对未设 env 的生产无行为差, 随下次窗口顺带带入。
   - crossover 维持 8192。大层 AR 收益路径收束为: 图内集成（把层 AR 固化进 graph, 消 host 阻塞往返）而非传输层调参 —— 见 ROADMAP 后续条目。

## 5. 过程坑（新记入 PITFALLS）

1. **GB10 统一内存 × 双 CUDA 上下文**: 生产 vllm 常驻即占满统一内存 → 旁路进程建 CUDA 上下文偶发 OOM, 表现为混合 `NOMEM/VERBS(-6)/CUDA(-11)` 且逐次不同（q1b 全 rank 失败, 重试即过）。**旁路 torch/NCCL 基准与常驻生产不共容**（torch set_device 直接 OOM）; NCCL RTR 超时报错是伴生症状, 勿误诊为 GID/子网问题。处置: 微基准用 ar2_probe（上下文极小, 加重试）; 需 NCCL 参考时取档期窗口数据或另开窗口。
2. docker exec 不传播 timeout 信号 → 跑前/跑后 pkill（run_probe.sh 已并入 run_reg.sh 纪律）。
3. defaults 非 0 预填 × "0 值才 env 回退" = env 静默死代码（§1.3, 模式级教训）。
